# spec/05 — 永続化 SSOT（SQLite / GRDB）の読み方

> **Status**: **実装済み**（2026-08-02）。`ladyland.sqlite` が永続化の SSOT
> **本体**: [05-persistence-ssot.kdl](05-persistence-ssot.kdl)
> **実装**: `ladyland/Sources/Ladyland/Audio/RackDatabase.swift`
> **テスト**: `ladyland/Tests/LadylandTests/RackDatabaseTests.swift`
> **裁定**: mako 2026-08-02「GRDB 導入しよう。ここが SSOT」

## 一行で

**目録は行、音色は内容アドレスの不変 blob。書き手は `DatabaseQueue` 1 本。**
音量ノブ 1 回で 21MB を書き直していたのを、行 1 つの upsert にした。

```
~/Library/Application Support/ladyland/ladyland.sqlite
├── rackState   単一行（総数・選択・出力・キー・LED）
├── slot        席（ロード済みのみ）→ stateHash で blob を参照
├── draft       席の棚（Track Drafts）→ 同じ blob を共有できる
└── blob        音色の実体。sha256 で内容アドレス・追記のみ・重複排除
```

## この spec が固定するもの — 3 層

| layer | 固定する Why |
|---|---|
| `store` | **なぜ SQLite / GRDB か**、および SurrealDB / SwiftData を採らなかった理由 |
| `schema` | 表の分け方（なぜ knobs は JSON 1 列か、なぜ blob を分けるか）・移行は追記のみ |
| `lifecycle` | 誰がいつ書くか（二層保存の維持）・GC の時期・rack.json からの移行・fail-open |

## 経緯 — 3 手で決まった

1. rack.json（単一 JSON）が **21MB** に育ち、音量ノブ 1 回でも全体を再エンコード
2. `.llw`（パッケージ + 内容アドレス blob、**DB なし**）案を検討し spec に起こした
3. **mako 裁定「GRDB 導入しよう。ここが SSOT」** で DB に決定。
   ②の核（内容アドレスの不変 blob）は SQLite の中へ持ち込んだ

②→③ で spec の題目が `.llw` から本ファイルに変わっている。
`.llw` というパッケージ形式は**採らなかった**が、その設計で正しかった部分
（blob を目録から分ける / 不変・内容アドレス）はそのまま生きている。

## 競合を「解決」せず存在させない

mako 裁定 2026-08-01「データアクセスをチョッパヤかつ、並行性の競合は気にしたくない」への答え:

1. **演奏中の正はメモリの `InstrumentRack`**。DB を読むのは起動時の 1 回だけ
   → read/write 競合が原理的に起きない（レンダースレッドを DB で止めない）
2. **書き手は `DatabaseQueue` 1 本**。GRDB は生の接続を渡さないので、直列化は
   ライブラリの構造として保証される — 自前のロックが 1 つも要らない
3. **blob は不変・内容アドレス** → 上書きが存在しないので競合も存在しない

結果、旧 JSON 時代の回避策が 3 つ消えた: バイト列 dedup / `saveGeneration` の
追い越しガード / detached エンコード。

## 二層保存は維持する（ここは安くならない）

`fullState` を **AU に問い合わせる**コストは保存層と無関係
（design/06 §8「パツパツ」の真犯人）。したがって:

| | 契機 | 書くもの | AU に触る |
|---|---|---|---|
| **軽い保存** | 選択 / 音量 / 並び替え / 割当 など 18 経路 | 目録の行だけ | ❌ |
| **重い保存** | プラグイン画面を閉じた / 30 秒 / 終了時 | 目録 + blob | ✅ |

⚠️ **軽い保存は `stateHash` を NULL で上書きしてはいけない**（blob を書いていないため）。
踏むと再起動で音色が消える — テストで固定してある。

## 実測で設計を 1 つ覆した（2026-08-02）

**AU は中身が変わっていなくても `fullState` のバイト列を変えて返すことがある**（内部カウンタ等）。
内容アドレスなので毎回 新しい blob が積まれ、**重い保存 2 回で 9MB の孤児**が出た。
30 秒タイマー × 40 分のセット = 80 回なら数百 MB になる計算。

当初は「GC は起動時だけ」（ライブ中にファイルを触らない原則）としていたが、
それでは本番中に肥り続ける。**行の DELETE はファイル操作ではなく同じ直列キュー内の
安い書き込み**なので、重い保存のたびに同一トランザクションで回収する方針へ変更した
（KDL の `gc-on-every-heavy-save` が `gc-at-launch-only` を supersede）。

SQLite は DELETE でファイルを縮めない（空きページを再利用する）ため、
実際に縮める `VACUUM` は全体書き直しになる **起動時だけ**に限る。

## 移行と後戻り

起動時に DB が空で `rack.json` があれば取り込む（1 度きり）。
**`rack.json` は消さない** — 8/8 を挟む変更なので後戻りできる状態を残す。
DB が開けなければ `startupError` を出して**保存なしで演奏は続行**する（fail-open —
本番では音を止めない方が正しい）。

## 持ち出す姿 — lldata スナップショット（実装済み 2026-08-02）

上の「バックアップ」問題への答え。**DB は動いている状態の SSOT、lldata は持ち出す控え**と役割を分ける。

```
lldata-snapshot-2026-08-02-0040.kdl   ← 設定 → スナップショットタブ から書き出し
```

- **自己記述** — 先頭の `schema` ノードがこのファイルの読み方を持つ（人が読んで分かる）
- **席 1 ノード = 部分ロードの単位**。読み込みは**必ず中身を見せて選ばせてから**入れる
  （「開いた瞬間に全部入れ替わる」を作らない — ライブ機材で一番怖い操作）
- **音色は内容アドレス**なので、同じ音色の base64 はファイル内に 1 回しか現れない
  （実データ: 22 席 + 17 棚 → blob 39 個 / 21MB）
- **音色を外す**と構造だけの軽いファイル（git で差分が読める）
- **知らない版は開かない**（半端に読んで席を壊さない）

⚠️ **Swift に成熟した KDL パーサが無い**（2026-08-02 調査）。全仕様は要らないので、
**自分が書き出した部分集合だけを読む**最小パーサ（`KDLMini`）を同梱している。
知らない構文に出会ったら黙って無視せずエラーにする。
